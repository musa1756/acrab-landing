# План миграции Acrab Landing на Astro, React и Tailwind CSS

## 1. Цель

Перенести существующий статический лендинг Acrab на технологическую основу,
совместимую с подходом шаблона
[`di-sukharev/vibe`](https://github.com/di-sukharev/vibe), не ухудшая SEO,
платёжный сценарий, юридические страницы и стабильность зарегистрированных URL.

Целевая модель рендеринга:

- Astro SSG генерирует публичные страницы в готовый HTML;
- React используется только для интерактивных клиентских компонентов;
- платёжный сценарий `/buy` работает как React CSR island;
- сайт собирается через Bun в каталог `dist`;
- Timeweb публикует содержимое `dist` как статический сайт;
- backend, база данных и платёжные Edge Functions остаются существующими.

Полный CSR для всего лендинга не используется. Он не нужен статическим страницам
и создаёт риски для SEO, метаданных, настоящего HTTP 404 и маршрутов,
зарегистрированных в Apple.

## 2. Что переносим из подхода `vibe`

Используем:

- Bun;
- Astro;
- React 19;
- TypeScript;
- Tailwind CSS 4;
- компонентную структуру;
- разделение статических страниц и клиентской интерактивности;
- сборку перед публикацией;
- автоматические проверки результата сборки.

Не переносим:

- backend шаблона;
- Prisma;
- отдельный PostgreSQL;
- встроенную авторизацию шаблона;
- Terraform;
- полный каталог shadcn/ui;
- TanStack Router;
- TanStack Query, пока у сайта нет сложного серверного состояния;
- отдельный `webapp` workspace.

Supabase Auth, `tochka-payment` и `tochka-payment-webhook` продолжают быть
источниками истины для авторизации и оплаты.

## 3. Инварианты миграции

Во время переноса нельзя нарушить следующие условия:

1. Все существующие публичные URL сохраняются.
2. `/buy` и `/support` продолжают открываться по адресам, зарегистрированным в
   Apple.
3. `/buy`, `/offer`, `/consent` и `/get` остаются `noindex`.
4. Каждая индексируемая страница сохраняет уникальные `title`, description,
   canonical URL и Open Graph metadata.
5. Главная страница сохраняет JSON-LD `MobileApplication`.
6. `/robots.txt` и `/sitemap.xml` отдаются как самостоятельные файлы.
7. Несуществующий адрес возвращает настоящую страницу 404, а не главную
   страницу приложения.
8. Юридический текст `/privacy` не редактируется в рамках технической миграции.
9. Платёжные секреты не попадают в браузер. Публичный Supabase anon key может
   оставаться клиентским.
10. Клиент не подтверждает оплату самостоятельно. Итоговый статус продолжает
    определять серверный webhook.
11. Существующие изображения не перекодируются без отдельной причины.
12. Незакоммиченное изменение `assets/changelog/1-4.png` сохраняется и не
    перезаписывается.

## 6. Этапы миграции

### Этап 0. Зафиксировать исходное состояние

- Создать отдельную ветку `codex/migrate-landing-astro`.
- Не включать существующее изменение `assets/changelog/1-4.png` в технические
  коммиты миграции.
- Запустить текущую проверку `python3 tools/check_site.py`.
- Снять скриншоты всех страниц на desktop и mobile.
- Записать текущие ответы ключевых маршрутов и итоговые URL после redirect.
- Проверить вручную текущий сценарий `/buy` до момента перехода на платёжную
  страницу.

Критерий завершения: исходная версия проходит проверки, а визуальный и
функциональный baseline сохранён.

### Этап 1. Добавить инфраструктуру сборки

- Создать `package.json`.
- Зафиксировать версию Bun.
- Установить Astro, React, TypeScript и Tailwind CSS.
- Создать `astro.config.mjs` и `tsconfig.json`.
- Настроить `trailingSlash: "always"`, если этого требует поведение Timeweb.
- Перенести статические ассеты, `robots.txt` и `sitemap.xml` в `public`.
- Добавить команды:

```json
{
  "scripts": {
    "dev": "astro dev",
    "build": "astro check && astro build",
    "preview": "astro preview",
    "typecheck": "astro check",
    "test": "bun test",
    "check": "bun run typecheck && bun run test && bun run build"
  }
}
```

Критерий завершения: пустая Astro-оболочка собирается в `dist` и открывается
локально.

### Этап 2. Перенести общий каркас и стили

- Создать `BaseLayout.astro`.
- Передавать в layout `title`, description, canonical, robots и Open Graph
  поля.
- Вынести `SiteHeader` и `SiteFooter`.
- Вынести цвета, размеры, типографику и отступы в CSS tokens.
- Подключить Tailwind без немедленного переписывания всех существующих стилей.
- Сначала сохранить визуальный результат, затем постепенно заменять повторяемые
  CSS-блоки компонентами и utility-классами.

Не выполнять глобальную автоматическую замену 1242 строк текущего CSS. Такой
перенос создаст визуальные регрессии и затруднит проверку причин изменений.

Критерий завершения: header, footer и базовая сетка совпадают с исходником на
desktop и mobile.

### Этап 3. Перенести публичные контентные страницы

Переносить по одной группе:

1. `/support` и `/about`;
2. `/learn-arabic`, `/arabic-alphabet`, `/fusha`, `/arabic-app`;
3. главную страницу `/`;
4. `/offer`, `/consent`, `/privacy`;
5. `/404`.

Для каждой страницы:

- перенести HTML без изменения смысла текста;
- заменить повторяемую разметку на компоненты;
- сохранить абсолютные пути к ассетам;
- сохранить семантические теги и доступность;
- проверить metadata;
- сравнить скриншоты до и после;
- проверить отсутствие клиентского JavaScript, если он странице не нужен.

Критерий завершения: все контентные страницы присутствуют в готовом HTML и
визуально соответствуют исходнику.

### Этап 4. Перенести платёжный сценарий `/buy`

- Оставить metadata, заголовки и юридические ссылки в статическом Astro HTML.
- Вынести интерактивный сценарий в `PaymentFlow.tsx`.
- Подключить компонент через `client:load`.
- Разделить код на:
  - состояние шагов;
  - Supabase API;
  - Tochka API;
  - отображение ошибок;
  - форматирование тарифов;
  - проверку принятия документов.
- Сохранить текущие различия ошибок `422`, `429` и `5xx`.
- Не сохранять access token в `localStorage`.
- Не добавлять клиентское подтверждение успешной оплаты.
- Сохранить защиту страницы от встраивания во frame.
- Пересобрать CSP с учётом сгенерированных Astro/Vite файлов. Не использовать
  постоянно меняющийся inline-script hash, если скрипт можно вынести в отдельный
  собранный файл.

Критерий завершения: сценарии ввода почты, OTP, выбора тарифа, принятия условий,
создания платежа и обработки ошибок совпадают с текущим поведением.

### Этап 5. Перенести `/get`

- Сохранить текущую логику определения платформы и redirect.
- Оставить страницу `noindex`.
- Разместить redirect-логику в отдельном клиентском модуле либо небольшом
  React-компоненте только при наличии реальной пользы.
- Проверить fallback, если автоматический redirect заблокирован.

Критерий завершения: маршрутизация в App Store, RuStore и fallback работает на
тех же устройствах, что и до миграции.
### Этап 6. Адаптировать автоматические проверки

- Изменить `tools/check_site.py`, чтобы он проверял собранный каталог `dist`, а
  не исходные `.html`.
- Проверять наличие всех 12 маршрутов.
- Проверять уникальность metadata индексируемых страниц.
- Проверять `noindex` служебных страниц.
- Проверять canonical URL.
- Проверять JSON-LD на главной.
- Проверять все внутренние ссылки и ассеты.
- Проверять покрытие sitemap.
- Проверять настоящий 404.
- Добавить unit-тесты чистых функций платёжного сценария.
- Добавить минимальный browser smoke test для `/buy`.

Критерий завершения: намеренное удаление страницы, canonical, ассета или
`noindex` приводит к падению проверки.

### Этап 7. Настроить CI

CI должен выполнять:

```text
bun install --frozen-lockfile
        ↓
bun run typecheck
        ↓
bun run test
        ↓
bun run build
        ↓
python3 tools/check_site.py dist
```

Артефактом CI является только каталог `dist`.

Критерий завершения: pull request нельзя объединить при ошибке типов, тестов,
сборки, ссылок или metadata.

### Этап 8. Подготовить Timeweb

- Установить корень проекта на репозиторий `acrab-landing`.
- Установить build command `bun install --frozen-lockfile && bun run build`.
- Установить output directory `dist`.
- Не включать SPA fallback на `index.html`.
- Проверить поддержку directory index и trailing slash.
- Сохранить домен `acrab.ru` и действующие TLS/DNS настройки.
- Сначала развернуть preview deployment.

Критерий завершения: preview отдаёт статические страницы, `/robots.txt`,
`/sitemap.xml`, `/buy`, `/support` и настоящий 404.

### Этап 9. Предрелизная проверка

Проверить:

- desktop и mobile layout;
- клавиатурную навигацию;
- reduced motion;
- загрузку всех изображений;
- App Store, RuStore и TestFlight ссылки;
- Telegram и email на странице поддержки;
- все canonical URL;
- Open Graph preview;
- JSON-LD;
- `/buy` без авторизации;
- `/buy` с существующим аккаунтом;
- неверный OTP;
- rate limit;
- отказ API;
- выбор месячного и годового тарифа;
- отказ пользователя принять документы;
- redirect на Tochka;
- возврат после отмены платежа;
- отсутствие секретов в `dist`;
- отсутствие исходных карт и служебной информации, если они не нужны в
  production.

Критерий завершения: новая версия функционально эквивалентна старой и проходит
все автоматические проверки.

### Этап 10. Переключить production

- Зафиксировать production commit.
- Выполнить production build из чистого рабочего дерева.
- Развернуть `dist`.
- Проверить основные URL непосредственно на `https://acrab.ru`.
- Проверить `/buy` и `/support` без изменения зарегистрированных адресов.
- Проверить HTTP status отсутствующего URL.
- Проверить Search Console и Yandex Webmaster после публикации.
- Сохранить возможность быстрого отката на предыдущий статический артефакт.

Критерий завершения: production работает на новой сборке, а предыдущий артефакт
остаётся доступен для отката.

## 7. Стратегия коммитов

Миграцию разбить на небольшие проверяемые коммиты:

1. `build: scaffold astro application`
2. `refactor: extract shared layout and design tokens`
3. `refactor: migrate support and changelog pages`
4. `refactor: migrate search landing pages`
5. `refactor: migrate product home page`
6. `refactor: migrate legal pages without copy changes`
7. `refactor: migrate payment flow to react island`
8. `test: validate generated routes and metadata`
9. `ci: build and verify astro output`
10. `docs: update hosting and development instructions`

Каждый коммит должен собираться и проходить актуальные проверки. В один коммит
не объединяются инфраструктура, визуальный редизайн и изменение платёжной
логики.

## 8. Основные риски

### SEO-регрессия

Причина: контент или metadata переносятся в клиентский React.

Контроль: индексируемый текст и metadata генерируются Astro на этапе сборки и
присутствуют в `dist/*.html`.

### Поломка Apple URL

Причина: изменение trailing slash, redirect или маршрутов.

Контроль: автоматическая и production-проверка точных адресов `/buy` и
`/support`.

### Поломка CSP на `/buy`

Причина: Astro/Vite изменяют способ подключения JavaScript.

Контроль: отдельная политика для платёжной страницы и проверка production
bundle без ослабления до небезопасного `unsafe-inline`.

### Изменение платёжного поведения при рефакторинге

Причина: одновременный перенос UI и бизнес-логики.

Контроль: сначала покрыть текущие переходы и ошибки тестами, затем переносить
логику без изменения контрактов API.

### Визуальные регрессии

Причина: полная одномоментная замена CSS на Tailwind.

Контроль: постепенный перенос, скриншотное сравнение и сохранение существующих
CSS-правил до появления эквивалентной реализации.

### Неправильная конфигурация Timeweb

Причина: SPA fallback или публикация корня репозитория вместо `dist`.

Контроль: preview deployment и HTTP-проверки до переключения production.

## 9. Критерии полной готовности

Миграция завершена только когда:

- все 12 маршрутов доступны;
- все проверки проходят;
- production build воспроизводим через Bun;
- публичные страницы содержат основной контент без выполнения JavaScript;
- React загружается только на интерактивных страницах;
- платёжный сценарий работает без функциональных изменений;
- SEO metadata и sitemap сохранены;
- юридический текст не изменён;
- отсутствующий маршрут возвращает 404;
- Timeweb публикует `dist` без SPA fallback;
- документация описывает новую локальную разработку, сборку и deployment;
- старые исходные HTML-файлы удалены только после проверки production-equivalent
  Astro-страниц;
- предыдущая production-версия доступна для отката.

## 10. Итоговое техническое решение

Лендинг остаётся статическим с точки зрения пользователя, поисковых систем и
хостинга. Astro превращает компонентные исходники в готовый HTML. React
используется как client-side слой только там, где есть состояние и API-вызовы.
Это даёт компонентную разработку и современный стек `vibe`, не превращая
маркетинговый сайт в SPA и не ухудшая его поисковую и эксплуатационную модель.
